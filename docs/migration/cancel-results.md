# Cancel migration checkpoint

Cancel is the twenty-first Spring Modulith business module. The live hybrid retains the `ts-cancel-service:18885` address behind a reversible proxy; `X-Cancel-Backend: module` identifies the active backend. The module uses published Orders, OrderOther and Inside Payment APIs. It keeps the legacy User service as a remote dependency for a standard-order cancellation.

The deployed Cancel JAR differs from the checked-out source in its order date fields, so implementation and comparisons used the deployed behavior. An isolated candidate passed 73 contract checks covering standard and OrderOther refund quotes and cancellation states, security, existing orders, drawback records, repeat cancellation, and the 21-module dependency graph. Live Orders, OrderOther and wallet `addMoney` collections were backed up before cutover. The rollback rehearsal switched only Cancel to legacy, confirmed the inactive module rejected a mutating request, cancelled a synthetic paid order, returned to module mode, and confirmed both legacy and module cancellations remained visible. The full checkpoint and Maven tests passed.

A synthetic paid order was also cancelled through browser-facing port 8080. Both the refund quote and cancellation returned HTTP 200 with `X-Cancel-Backend: module`; the order became cancelled and the refund appeared in the wallet. Run `python docs/migration/verify_cancel_ui.py` to repeat that test with a disposable order. In the UI, open **Order List**, choose **Cancel** on a cancellable order, and inspect the `GET /api/v1/cancelservice/cancel/{orderId}/{loginId}` response header in Developer Tools. `python docs/migration/verify_checkpoint.py` checks the direct route, security and module graph. `python docs/migration/verify_cancel_rollback.py` repeats the rollback rehearsal. Manual routing commands are `python docs/migration/hybrid_routing.py legacy cancel` and `python docs/migration/hybrid_routing.py module cancel`.

The deployed service changes the order status before calculating its refund. As a result, cancelling an unpaid order can credit 80% of its price. The module retains this behavior so side-by-side results match; it is a defect to fix separately with an agreed refund rule. Cancellation and wallet drawback still write to separate Mongo databases without an atomic transaction, matching the legacy service. Notification sending remains disabled as it is in the deployed JAR. Production consolidation needs explicit failure and concurrency tests for these operations.

Next candidate: Rebook, after inspecting its deployed runtime and dependencies. WaitOrder remains pending because it is absent from the running Compose stack and its configured MySQL database is unavailable.
