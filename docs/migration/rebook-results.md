# Rebook migration checkpoint

Rebook is the twenty-second Spring Modulith business module. The live `ts-rebook-service:18886` address now points through an independent compatibility proxy to the shared host. `X-Rebook-Backend: module` identifies the active backend. The module uses published Orders, OrderOther, Station, Travel, Travel2, Seat and Inside Payment APIs. It has no own database.

The deployed JAR differs from the checked-out source: it uses `Date` fields and resolves station names before asking Travel or Travel2 for trip details. An isolated candidate passed 74 checks covering missing and unsuitable orders, same-price changes, cheaper changes and refunds, higher-fare quotes, both order families, replacement order retention and the 22-module dependency graph. The live Orders, OrderOther and wallet payment collections were backed up before cutover. An independent rollback rehearsal changed only the Rebook route to legacy, verified the inactive module rejected writes, changed a synthetic order through legacy, returned to module mode and changed another order. Both changes remained visible.

Two deployed defects were reproduced and deliberately fixed in the module. The legacy `/rebook/difference` method sets its HTTP headers argument to `null`, then dereferences it, so paying a fare difference returns HTTP 500. The legacy cross-family path calls `POST` on the Orders or OrderOther delete endpoint, which returns HTTP 405 and makes Rebook return HTTP 500. The module completes these paths through local APIs. It creates a replacement order before removing the original and attempts to remove that replacement if the original deletion fails. Those writes still span separate Mongo databases, so they are not atomic; production acceptance needs fault injection and concurrent-change tests.

The deployed Order List JavaScript omitted `loginId` from Rebook requests. A cheaper replacement could therefore credit an empty wallet account. The UI image now includes the logged-in ID and removes a trailing space in the Rebook URL. The launcher keeps this patched image when resuming the hybrid.

Verification completed: the full checkpoint and Maven tests passed; a synthetic `POST /api/v1/rebookservice/rebook` through port 8080 changed an order with `X-Rebook-Backend: module`. Additional browser-facing synthetic checks verified refund to the requested user, fare-difference payment, and replacement OrderOther creation. The rollback evidence and candidate comparisons are under ignored `ts-modulith/target/evidence/`.

To verify manually, open **Order List**, select **Change** on a paid, uncollected order, choose a new train and confirm. In Developer Tools, inspect `POST /api/v1/rebookservice/rebook` and, for a higher fare, `POST /api/v1/rebookservice/rebook/difference`; each response should include `X-Rebook-Backend: module`. Refresh Order List to confirm the changed ticket. Automated commands: `python docs/migration/verify_checkpoint.py`, `python docs/migration/verify_rebook_ui.py`, and `python docs/migration/verify_rebook_workflows.py`. The latter two create synthetic orders and wallet records. Rollback rehearsal: `python docs/migration/verify_rebook_rollback.py`; manual route switches: `python docs/migration/hybrid_routing.py legacy rebook` and `python docs/migration/hybrid_routing.py module rebook`.

WaitOrder remains pending because it is not in the running Compose stack and its configured MySQL database is unavailable. The next available candidate in the plan is Assurance, subject to inspection of its deployed dependencies.
